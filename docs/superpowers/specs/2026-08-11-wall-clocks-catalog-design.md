# Каталог-витрина настенных часов — дизайн

Дата: 2026-08-11

## Цель

Публичный сайт-каталог настенных часов (тот же ассортимент, что продаётся на Wildberries), без встроенной оплаты. Заказ — звонок, WhatsApp, Telegram или переход на карточку товара на WB. Обновляется автоматически, без ручной работы пользователя после первичной настройки.

## Источники данных

**Единственный источник — WB Content API** (`https://content-api.wildberries.ru`), эндпоинт `POST /content/v2/get/cards/list` с фильтром `{withPhoto: 1, objectIDs: [625]}`. Один ответ отдаёт сразу всё, что нужно карточке: `nmID`, `title`, `description`, `photos[].big`. Токен предоставляет пользователь, хранится как секрет GitHub Actions, в репозиторий не попадает.

**Изменение от 2026-08-13:** изначально каталог собирался из гугл-таблицы (`wb-google-sheets-webapp`), а WB API использовался только ради фото. Живая проверка (выборка 300 карточек: у 300 есть фото, название и описание длиннее 300 знаков) показала, что таблица для сайта не нужна — она выпилена из сборки вместе с модулями `sheets.js` и `filter.js`. Минус один секрет в GitHub Actions и одна точка отказа. Следствие: тексты на сайте — ровно те, что уже опубликованы на WB; чтобы поправить текст на сайте, надо поправить карточку на WB.

**Почему не эксель-выгрузка WB:** ручная выгрузка противоречила бы требованию «обновляется само раз в 24 часа».

## Правило отбора товара в каталог

Товар попадает в каталог **тогда и только тогда**, когда WB отдал его карточку в категории «Часы настенные» (subjectID 625) и у карточки есть хотя бы одно фото. Никаких других фильтров: что живёт на WB, то и на сайте. Колонка «Статус ИИ» в таблице как фильтр не используется (заполняется вручную и ненадёжна — часто пустая даже у реально живых карточек).

Товары без фото в каталог не попадают (никогда не показываем карточку без картинки).

## Данные карточки товара

Из ответа WB используется: `title` (название), `nmID` (артикул), `description` (описание). Цена — не из WB:

- **Фото** — `photos[0].big` (первое/основное фото).
- **Описание** — на плитке в общем списке показывается коротким превью (первые ~150 символов, обрезка по CSS), на отдельной странице товара — полностью.
- **Цена** — на WB не запрашивается. Отображается статично и одинаково для всех товаров: ~~7000 ₽~~ **1890 ₽**, подпись «Доставка по всей России Бесплатная». Значение — константа в шаблоне сайта, меняется в одном месте при необходимости.

## Кнопки заказа (на каждой карточке)

1. **Позвонить** — `tel:+79266642121`
2. **WhatsApp** — `https://wa.me/79266642121?text=Здравствуйте! Интересуют часы «{Наименование}» (арт. {Артикул WB})` (номер в международном формате, без ведущей 8)
3. **Telegram** — `https://t.me/Podarki190`
4. **Купить на WB** — `https://www.wildberries.ru/catalog/{Артикул WB}/detail.aspx`

## Оформление заказа («Заказать» на странице товара)

Простая форма, без бэкенда и без хранения данных на сервере:

- Поля: ФИО, телефон, город и адрес доставки (свободный текст).
- Две кнопки отправки: **«Отправить в WhatsApp»** и **«Отправить в Telegram»** — обе собирают одно и то же сообщение (название и артикул товара, ФИО, телефон, город/адрес) и открывают `wa.me`/`t.me` с готовым текстом. Человек жмёт «отправить» сам, никакие данные никуда, кроме этого чата, не уходят.

**Отложено на потом (не в этом этапе):** картовые виджеты выбора ПВЗ СДЭК/Яндекс Доставка вместо текстового поля адреса. У пользователя уже есть аккаунт и договор с СДЭК — можно подключать без лишней бюрократии, но это требует API-ключ СДЭК и небольшой сервер-прокси (официальный виджет так устроен — ключ нельзя светить на статичном сайте), то есть уже не «чистый статический сайт». Вернуться к этому отдельным шагом после запуска каталога.

## Устройство сайта (важно для поисковиков — см. ниже)

Статический сайт, без бэкенда, но весь контент рендерится в готовый HTML на этапе сборки, а не дорисовывается в браузере через JS — иначе поисковики (особенно Яндекс) видят почти пустую страницу и не индексируют товары.
- `index.html` — список всех товаров, каждая плитка (фото, название, превью описания, цена) уже присутствует в HTML как обычная разметка. **Четырёх кнопок заказа на плитках нет** (замер 2026-08-13: одни только WhatsApp-ссылки с URL-кодированным русским текстом дали 2,2 МБ на 5359 плиток) — кнопки живут на странице товара, плитка ведёт туда. JS на этой странице только фильтрует уже отрисованные карточки по подстроке в названии (показывает/скрывает существующие DOM-узлы, ничего не подгружает и не дорисовывает) — без сервера, без пагинации. **Открытый вопрос:** товаров оказалось 5375, а не ~2500; после первой сборки замерить реальный вес `index.html` и, если он окажется тяжёлым для мобильного (ориентир — больше ~2 МБ), только тогда добавлять пагинацию или разбивку по категориям. Не усложнять заранее.
- Отдельная HTML-страница на каждый товар (`/tovar/<Артикул WB>/index.html` — используем сам nmID как адрес страницы: он уже гарантированно уникален и не требует транслитерации названия) — фото, полное описание, все 4 кнопки, свой `<title>` и `<meta description>` (из названия и описания товара). Даёт каждой модели часов собственный индексируемый URL, по которому её может найти прямой поисковый запрос.
- `sitemap.xml` — генерируется тем же скриптом сборки, перечисляет все страницы (общий список + все товарные), чтобы поисковики быстрее находили и индексировали новые/изменившиеся страницы.
- `robots.txt` — разрешает индексацию всего сайта.

## Сборка и публикация

- Репозиторий на GitHub, хостинг — **GitHub Pages** (бесплатно).
- **GitHub Actions**: workflow с `schedule` (раз в 24 часа) + `workflow_dispatch` (ручной запуск по кнопке в интерфейсе GitHub) — постранично выкачивает каталог с WB API → генерирует `index.html`, страницы товаров и `sitemap.xml` → публикует на GitHub Pages. Полный проход замерен на живом API 2026-08-13: **5375 карточек с фото за 9,5 минут** (54 страницы по 100). Для суточного обновления нормально (лимит job в GitHub Actions — 6 часов).
- Секрет (`GITHUB_SECRETS`, не в коде): токен WB API. Единственный.

## Обработка ошибок

- WB API недоступен или отдал ошибку (в т.ч. рейт-лимит) → шаг сборки падает, сайт остаётся на предыдущей опубликованной версии (GitHub Pages не перезаписывается при неуспешном workflow), следующая попытка — по расписанию или руками через `workflow_dispatch`.
- У отдельной карточки нет фото → она просто не попадает в текущую сборку (не весь процесс), появится в каталоге, когда фото на WB появится.

## Тестирование

Тесты на `node:test` + `node:assert/strict`, без фреймворков, на фиктивном ответе WB API (реальная сеть не дёргается) проверяют:
- товар без фото не попадает в сборку;
- пагинация идёт по курсору последней карточки и останавливается на неполной странице;
- ссылки WhatsApp/WB/Telegram/tel собираются в правильном формате;
- цена в выводе всегда `1890` со зачёркнутой `7000`, независимо от `Цена` в таблице;
- у каждого товара генерируется отдельная HTML-страница с непустыми `<title>` и `<meta description>`;
- `sitemap.xml` содержит запись для каждой сгенерированной страницы товара.

## Первичная настройка (вне кода, шаг при внедрении)

- Помощь пользователю в регистрации аккаунта на GitHub (аккаунта пока нет).
- Создание репозитория, включение GitHub Pages (Source: GitHub Actions) в настройках репозитория.
- Добавление секрета (WB API token) в настройки репозитория.
